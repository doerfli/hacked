UI refactoring proposal

Hacked?

A full move from AppCompat XML layouts to Jetpack Compose on Material 3, with a dark theme that follows the system and an in-app override. The brand green and orange stay; the status colours stay semantic and fixed, because in a breach checker colour carries meaning.

What the current UI does wrong

Findings from reading every layout, adapter and fragment in app/src/main/res and ui/.

Dark mode is impossible today

The theme is pinned to Theme.AppCompat.Light.NoActionBar, there is no values-night, and text colour is hardcoded to @android:color/black in five layouts plus Color.Gray and Color.Red inside the Compose breach card.

The overview cannot scroll

fragment_overview.xml stacks three nested fragments in a ConstraintLayout at fixed heights — 100dp for passwords, 150dp for breaches. Small screens and large system font sizes clip the content with no way to reach it.

Two image loaders ship at once

Picasso loads breach logos in the RecyclerView adapter; a deprecated accompanist-coil 0.15.0 loads the same logos in Compose. Same asset, two caches, two decoders.

Rendering state through visibility flags

Screens toggle View.GONE across six sibling views to express one state. PwnedPasswordFragment tracks its result through four independent visibility calls, so an error and a result can both be on screen.

Deprecated across the board

setHasOptionsMenu, onActivityCreated, PreferenceFragment, LocalBroadcastManager, getColor(int), and notifyDataSetChanged on every list update rather than diffing.

Cards without hierarchy

Every surface is a white CardView on a white background, separated only by a 0.5dp grey section_header shape. Nothing distinguishes a compromised account from a clean one except an 8dp colour bar at the far-left edge.

The redesigned screens

Each screen shown in both themes, as it would render in Compose with Material 3. The three overview panels become three destinations in a navigation bar — Accounts, Passwords, Leaks — which removes the fixed-height nesting entirely and gives each one a full scrolling surface.

Accounts

replaces OverviewFragment + AccountsFragment + fragment_overview.xml

  • A status banner leads with the one number that matters — unresolved breaches — so the answer is readable before any scrolling.
  • The left colour bar becomes a status dot plus a count badge: breached, acknowledged-only, clean, never checked. The badge carries the count in a scannable right-hand column; the supporting line names the state in words, so the row never relies on colour alone and never states the number twice.
  • Adding an account moves from an inline Group visibility toggle to a FAB opening a bottom sheet.
  • Last-checked time sits under the section label instead of baseline-aligned against the title.

Leaks

replaces AllBreachesFragment + BreachesFragment + two card layouts

  • Named Leaks, not Breaches — this is HIBP's catalogue of breached sites, reference data rather than your own exposure, which the Accounts tab already reports.
  • Two adapters and two card layouts driven by a compactView boolean collapse into one composable with an expanded flag.

Four palettes to choose between

Chosen: A in light, D in dark. The screens further up are drawn that way — verdant green by day, deep teal at night. It is an unusual split but a coherent one: green carries the brand where the ground is bright, and teal holds up better than green against a near-black surface, where the "clean" status green would otherwise sit uncomfortably close to the primary. The section below is the comparison the choice came from.

The same Accounts screen with the same content, so only colour varies. In all four, the semantic status set is identical and untouched — breached red, acknowledged amber, clean green, unchecked grey. Those are the app's load-bearing colours; what changes below is only the chrome around them, which is why a quieter chrome can make the statuses read louder.

A · Verdant

the current proposal — brand-continuous

dark

  • The one real cost: green is also the "clean" status, so primary and a status colour share a hue family. The FAB and the clean dot sit in the same neighbourhood.

App icon — the leaking password

Chosen: 3c · Receding, in the erosion set below — characters intact but each smaller than the last, retreating out of the field. Nothing is damaged; the password is simply going away. The sections here are the exploration the choice came from.

One idea, six drawings: a password field that is no longer holding what it was given. Asterisks are the only glyph that says "password" without a word, and nothing here is a loose dot — the secret comes apart by tipping, breaking, eroding or slipping through a gap instead.

Every icon is shown as a launcher tile, at the small size where most icons fall apart, and as an Android 13 themed (monochrome) variant — the silhouette test, since a themed icon loses every colour cue. All artwork sits inside the 72dp safe zone of a 108dp adaptive icon, so nothing is clipped by a round, squircle or squared mask. The background is held constant so you are comparing drawings, not colours.

1 · Come loose

Two characters still on the field, one tumbled off the end. The clearest reading of the six — something that was held is now out — and the diagonal of the fallen glyph gives the tile a direction to follow.

the one you already picked · three glyphs is a lot of detail at 48px

2 · Unmasked

The mask holds for two characters and then simply fails — the third is a plain readable letter. Nothing moves, nothing breaks; the secret is just no longer a secret, which is exactly what a pwned password is.

most conceptually exact · the letter needs colour to register as the odd one out

3 · Eroded

Four characters losing an arm each as the eye moves right, until nothing is left but a stub. Reads as decay over time rather than a single event — apt for a password that has been sitting in a dump for years.

the only one with a left-to-right narrative · subtle, and easy to misread as an incomplete drawing

4 · Tipped

The whole field tilted, so the characters are sliding off the low end under their own weight. Gives the tile a diagonal composition, which stands out sharply in a home screen grid of upright icons.

most dynamic composition · the tilt can read as a rendering error

5 · Split

A single character filling the tile, with one arm snapped off and thrown clear. The boldest and simplest shape of the six — one glyph, no field, no supporting cast — which is what makes it survive being 40px on a crowded home screen.

best at the smallest sizes · loses the "field" context that makes it a password

6 · Slipping through

A gap has opened in the field and one character has already gone through it. The only variant that shows the breach as well as the loss — there is a hole, and here is what went out of it.

tells the whole story in one tile · the gap must stay wide or it disappears when scaled

Icon 3 — erosion, four ways

3c is the chosen drawing. Same idea each time: the characters weaken as the eye travels right, so the row itself is the story. What differs is how a character weakens — by losing arms, losing weight, losing size, or losing its grip on its own centre.

3a · Losing arms

Three strokes, then two, then one, then a stub. The original. Each glyph is still full-size and full-weight, so the loss is purely structural — pieces are missing, not faded.

most literal erosion · can look like an unfinished drawing

3b · Thinning

Every character keeps all three arms; what drains away is weight. The row fades to a hairline rather than breaking, which reads as something wearing out over years — closer to what an old leaked password actually is.

most graceful of the four · the hairline vanishes at 48px and in monochrome

3c · Recedingchosen

Each character intact but smaller than the last, as though retreating into the distance. The strongest sense of depth of the four, and the only one where no glyph is ever damaged — the password is not broken, it is disappearing.

cleanest drawing · a diminishing row can read as a loading animation

3d · Coming apart

Nothing is lost, thinned or shrunk — the arms simply drift out of register with each other until the last character is barely holding together. Every stroke is still present, which keeps the monochrome variant as strong as the colour one.

best monochrome of the four · the drift is subtle at small sizes

Icon 5 — one character, four breaks

A single glyph filling the tile, with no field beneath it. That is what makes this direction the most legible at small sizes and the least specific about passwords — so the burden falls entirely on how convincingly it breaks.

5a · Thrown clear

One arm snapped at the centre and flung away at a new angle. The original. The most violent of the four, and the only one where a piece has genuinely left.

most obvious break · off-balance, the tile leans right

5b · Sheared

The glyph cut straight across and the halves slid past each other along the fault, with the cut line lit. Geologic rather than violent — something shifted underneath and the character no longer lines up with itself.

most striking at a glance · the offset halves can read as a print misalignment

5c · Hollowed

Every arm still there, but pulled back from a void where they used to meet. Nothing was taken from the outside — it failed at the join, which is the more accurate story for a password that was never attacked directly, only found in someone else's dump.

most balanced composition · needs the gap kept generous or it closes up

5d · Half solid

The left of the glyph is solid, the right side breaks into spaced marks — the same left-to-right decay as the icon 3 family, compressed into a single character. It is the one drawing that could serve as both a standalone icon and the seed of a set.

reads as one system with icon 3 · fewest strokes carrying the meaning

Migration order

Sequenced so the app builds and runs after every step. The theme lands first because it is what makes each ported screen verifiable in dark mode as it arrives.

01

Dependencies and theme

Add compose-material3, compose-bom, coil-compose, navigation-compose. Drop accompanist and Picasso. Write ui/theme/ — Color, Type, Theme, StatusColors.

02

Theme preference

Migrate SettingsFragment to AndroidX PreferenceFragmentCompat, add a Light / Dark / System list preference, apply through AppCompatDelegate.setDefaultNightMode.

03

Single Compose activity

NavActivity becomes setContent { HackedTheme { HackedApp() } } with a NavHost and a NavigationBar. The RxJava PublishProcessor nav bus is replaced by direct NavController calls.

04

Screens, one at a time

Accounts, then Account detail, then Passwords, then Leaks. Each ported screen deletes its fragment, its layout XML and its adapter in the same commit.

05

Sweep

Remove viewBinding, the CardView and RecyclerView dependencies, the navigation XML graph, and every remaining hardcoded colour.

Proposal only — no code changed. Mockups are HTML approximations of Compose output, not screenshots.
